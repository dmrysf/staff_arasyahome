# B2B Operations + Staff integration V1

## Design

1. Commercial lifecycle stays draft → finalized → cancelled. Finalize only freezes and posts the receivable. Production submission is a separate command; submitted orders remain finalized and cannot be commercially cancelled, even after production completion.
2. Submission locks company → commercial order, rechecks IAM, validates frozen manufacturing input, creates the canonical operational order/items/QR and initial timeline event, records the immutable handoff and replay reference, and commits once. No HTTP self-call, ledger write or finalized aggregate rewrite.
3. Durable one-to-one handoff keys plus canonical `(source_key, source_order_id)` uniqueness protect exactly-once business identity. Actor-scoped existing B2B order idempotency stores reference-only results. Same key/changed intent conflicts; new keys return the existing handoff without side effects. Cancellation shares the same row locks.
4. Source `b2b`, source order ID = commercial UUID, display order number = B2B order code. The source registry marks it internal; no Woo ID, heartbeat dependency or outbound commerce change.
5. The canonical item model supports arbitrary products, so curtain, drapery and other all map. Every line UUID, code/name, variant/color, cm dimensions, quantity and whole-line meters is retained. Nullable manufacturing context preserves kind and both line notes; company identity comes from the frozen company snapshot. Money/payment/account data never enters this context. Out-of-range/unrepresentable lines fail atomically with their line identity; no truncation or omission.
6. Additive migration `012_b2b_production_handoff.sql`: immutable one-to-one handoff with actor/time/request metadata; nullable manufacturing context on operational orders/items; internal source and two permissions; extend the existing production timeline action constraint. No duplicate stage state and no historical cascade.
7. `b2b.production.view` and `.submit` both require B2B application access and `b2b.orders.view`; no automatic grants. Dashboard only labels them.
8. GET/POST `/b2b/orders/{UUID}/production`. POST accepts only required positive `expectedVersion`; session, exact Origin, CSRF, idempotency and eligibility are server-owned. The request cannot set source, workflow, stage, owner or operational ID.
9. Staff keeps its existing lookup/QR/claim/transition paths and B2B label. Small rendering additions show frozen company/type/notes. Canonical workflow is validated by the existing service, starts at waiting, and remains the only workflow.
10. B2B order detail gets a permission-gated card near its header, explicit confirmation and refresh/focus revalidation of canonical progress. No production controls. Server cancellation capability is false after submission even for actors without production view.
11. Cancel after any handoff returns `409 ORDER_ALREADY_IN_PRODUCTION` before ledger reversal. No production cancellation, deletion or reset is introduced.
12. Submission never calls AccountLedger. Financial snapshots and balances are asserted unchanged in tests; finalize/cancel before handoff retain the accepted behavior.
13. TDD: lifecycle, replay/conflict/races, DB constraints, failure rollback, snapshots/inactive company, all line types, permissions/CSRF/origin/revocation, canonical Staff progress, financial/source isolation, RO/TR and 1440/768/390/360/reduced-motion. Run MySQL 8.4 and MariaDB 10.11, then existing regression gates.
14. Baseline artifacts: API 2.10.0 source `9044c5dc84ab3f885862c31ed5d87b3379115729`, api-deploy `18d0ff2d211076553842ce71fad20e41a6ca34e2`; Staff 2.3.1 deploy `37398bb11c09f92e98ddfe707621383f4b25c0d6`; B2B 0.4.1 source `ce4f9cf15b5debb82946f20afe9d83759748353f`, deploy `e11f3e31e3e7a0f32558eafaf7cb48eef8f6b942`; Dashboard 0.5.3 source `fca0ef94aa3e33df2cf7ac4b5e802277cf1779a4`, deploy `c6bb840e69446de472b49115fc88b1776d4a0325`. Retain additive schema, all handoffs and history on rollback. **After a real handoff, retain the guarded API even if frontends revert. API 2.10.0 lacks the cancellation guard. Revoking role permissions alone does not constrain Root. An unavoidable old-API rollback requires separately verified isolation of all B2B commercial writes, including Root, before activation; otherwise it is unsafe. Prefer a forward corrective Git release.** No destructive rollback.

Versions: API 2.11.0, B2B 0.5.0, Dashboard 0.5.4; Staff 2.3.2 for necessary context rendering. Visual/3D, inventory, production cancellation and financial extensions remain out of scope.

## Persistence and audit

`b2b_production_handoffs` contains immutable one-to-one commercial/operational identity, actor UUID/name snapshot, submission time, request ID and original idempotency key. A composite foreign key fixes source `b2b` and the commercial UUID as the canonical source ID; no handoff deletion/update endpoint exists. The existing production timeline records `production_submitted` with revision 0→1 and the initial stage label snapshot. Its actor/key uniqueness uses `b2b-production:` + SHA-256 of the request key so a Staff action's key cannot collide across command domains; the handoff retains the original key. B2B replay storage records references only, so reads always reflect current canonical progress. Expiry of replay rows cannot bypass durable business uniqueness.

Manufacturing context is nullable and whitelist-only. Staff receives frozen company legal name/code/country/tax ID, product identity, cm dimensions, whole-line meters/quantity, type and line/order production notes. Contact/address snapshots remain intact in the commercial aggregate; no live refresh, financial amount, payment, allocation, balance or terms is exposed to Staff. Unsupported representation fails before any write.
