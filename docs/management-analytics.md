## Employee facts and formulas

* Cutting success = the latest valid canonical **Tăiere (2) → Primire Croitorie (3)** completion. The final completing employee owns the **entire order**, exact canonical meter snapshot and known completed-line snapshot. Earlier transfer owners retain their own handling intervals, not a split of successful volume.
* Approved `fault_returned` invalidates the earlier completion in the current projection. Historical activity remains untouched. A later valid cutting completion again owns the entire order. A currently reopened, unfinished order has no current successful-completion numerator.
* Meters use integer thousandths and `DECIMAL`, never quantity × meters. A 12.300 m line with quantity 2 is 12.300 m. Average meters/order uses successful total / successful orders, rounded to thousandths. Missing historical line/meter snapshots are explicitly counted; incomplete average/rates are unavailable rather than guessed from current mutable lines.
* Only immutable approved `production_quality_events` enter quality KPIs. `cutting_fault` belongs to the responsible worker; detected-fault facts belong separately to the detector. A report/rejection alone creates neither fault numerator. Fault meters/lines are **cycle totals**; fault orders are distinct affected orders. Rework cycles, repeated cycles, distinct repeatedly affected orders and repeated-cycle meters are separate.
* Fault-meter rate = approved attributed fault meters / valid completed cutting meters. Fault-order rate = distinct attributed fault orders / valid completed orders. Fault-line rate = cycle fault lines / known completed lines. These are period flows, not causal cohort probabilities: numerator and denominator are shown, may concern different orders or cycles and can exceed 100%. Zero/missing denominator yields unavailable, never a score. Customer cancellation creates no fault numerator.
* Transfer initiated count uses request date; incoming/outgoing completed transfers use successful canonical QR verification date. Approved-but-unaccepted or cancelled transfers are not completed transfers.
* Period active handling clips ownership intervals to the selected range and subtracts the union of canonical blocking windows. Cutting-only handling is separate from all-stage handling. Final-completion duration samples describe the completing owner's final interval, not previous owners' time. No parallel employee duration is used as an attendance/payroll measure.
* Daily Romanian-calendar and ISO-week trends expose completed volume, active time, fault/detected meters and cycle counts. Employee detail provides bounded related-order pages, longest raw examples and canonical order drilldown. Primary departmental membership is **current**, not a fabricated historical affiliation.
* Department metric sets distinguish cutting, tailoring, packaging, delivery, finance activity, online activity and generic canonical activity. Finance/Online are never labeled meters-cut performance. Online supports only existing canonical `production_submitted` facts, not sales, PDF counts or order-entry corrections without source facts. Department manager wait unions each related order's approval windows once, clipped to the period; cross-department totals are not additive.

## Time and manager metrics

Canonical storage is UTC. Public analytics timestamps reuse the existing explicit ISO-UTC `Z` contract, including nested timeline/interval fields, never naive database strings interpreted in the browser's local timezone. A New York browser is tested against Romanian presentation. Business time is the duration intersecting current server-owned `business_hours` windows in **Europe/Bucharest**. Each calendar day's timezone offset is computed independently, so DST is not a naive local-string subtraction. Default schedule: Monday–Saturday 05:00–20:00; Sunday closed. Current configured hours are used at report time, not claimed as historical schedule snapshots.

Approval business windows alone extend each open day's closing time by Root's grace minutes; overlapping windows are unioned. 19:55 → 20:45 is 50 approval-business minutes with default grace, but only 5 normal employee-business minutes. Beyond 21:00, approval business time resumes at the next open day; closed Sundays receive no separate grace. A prior day's configured grace can cross midnight. Employee clocks never receive grace.

Active handling = ownership duration − union(transfer blocking, exception blocking, genuinely unavailable-source blocking). Overlapping blocking is subtracted once. Approval wait ends at the decision; transfer blocking ends at resolution/QR verification; exception blocking ends at resolution, not mere acknowledgment. Cancelled undecided attempts stop at known exception resolution rather than growing indefinitely. Separate wait categories are explanatory and **must not be summed** as if disjoint. `blockedUnion` is the non-overlapping normal-clock blocked measure.

Manager decisions use immutable exception attempts and immutable transfer-decision IAM audit, not a later mutable transfer cancellation status. Each attempt exposes its opening, decision, decider, `via`, prior rejected decision and order drilldown. Approved/rejected counts, request-type breakdown, backup-approver decisions and response distributions use decision dates. Re-review-after-rejection counts use the new attempt's opening date and link the old decision: they never mean “wrong decision.”

At a **new** request's opening, the exact existing `ApproverPolicy` captures active eligible recipients, effective authority/temporary backup via and opening UTC. Involved workers are excluded. A separate immutable marker distinguishes zero eligible recipients from unknown historical capture. Rebuild never infers historical recipients from today's roles. Period received count uses captured opening eligibility, not who happened to decide. Historical requests without capture make received metrics unavailable; known counts remain visible. Current pending recipient/elapsed metrics may include requests opened before the range and are explicitly labeled. Response distributions use mean, median and sample size; P25/P75 require N≥4, P90/P95 N≥20 (nearest rank), no empty-set zero or concealed outliers.

## Lifecycle, sources and B2B

Order timeline reads canonical stage/owner/quality activity, immutable approval attempts and cutting pool facts. QR creation is the earliest canonical QR timestamp. First real claim uses `claimed`, never a Root reassignment or backfilled claim. Final delivery is `production_completed`, never the cutting handoff. Document/PDF creation is unavailable when no canonical timestamp exists; QR is not mislabeled as PDF creation.

Completed QR→delivery and first-claim→delivery samples exclude unfinished orders. Open orders expose partial elapsed time through `asOf`. Active work, first-claim delay, pool-to-owner cutting wait, cutting active, approval, transfer, exception and union blocking are separate. Non-worker duration = normal QR lifecycle clock − active handling, floored at zero; it includes unclaimed gaps and is not wholly attributable to managers. Pool/cutting historical observations absent from canonical data remain unavailable. Manager/exception distribution samples are completed delivery cycles; cutting wait/active distributions are valid completed cutting cycles. N is always visible.

Source/company cohorts include orders related to the selected period via creation, cutting/delivery completion, overlapping ownership, quality, pool/source facts or request activity. Current whole lifecycle of those orders is measured, not clipped into a fabricated partial completion. They are **production cohorts, not sales totals**. Source names come from the canonical source catalog with a future-source key fallback. B2B grouping uses stable company UUID via a narrow read-only B2B identity adapter; names are frozen production-context observations (latest in cohort), not a tax/contact identity heuristic.

Company/source summaries expose sample size, median/mean/quartiles/tails, current known canonical production-line meter/line totals and missing observations. Related orders show import time/day, source, meters/line count and individual lifecycle for fair manual comparison. Comparable lines retain quantity for context without multiplying meters. No adjusted fairness/complexity score or favoritism label exists. Unknown firm/individual customer type is explicitly unavailable; no account balances leak into reports.

Canonical source-cancellation facts distinguish before/after recorded real work; cancellation is not employee fault. A canonical claim or already completed stage proves work, including historical Root-assigned orders completed without a `claimed` action. Bare assignment does not fabricate a real claim or work proof; physical work without any canonical fact is unknown. Accepted 015 invariant remains: source cancellation **after cutting starts** preserves internal production ownership/stage and `in_progress`; it does not terminate the worker's clock or fabricate final delivery. Genuine `unavailable` cancellation before work closes a partial cycle at its known source-cancellation timestamp. Historical cancellation facts remain visible in cohort counts even if a source later becomes active again. No full active-production cancellation/returns workflow is invented.

## Projections, performance and rollback

`analytics_order_projection` and `analytics_ownership_intervals` are derived/rebuildable. `analytics_approval_requests` / `analytics_approval_eligibility` are append-only future snapshots, not disposable history. Canonical activity, quality, attempts and IAM audit remain immutable. Capture runs in the **same canonical order transaction** after source/QR/cutting/handoff facts are written. Rebuild and writes serialize on the same order row lock; a stale rebuild cannot overwrite a newer committed event.

`php bin/rebuild-analytics.php [--batch=50]` uses bounded UUID keyset batches (1–500), one atomic transaction/order. It is rerunnable/idempotent, no automatic web-request migration/rebuild, no unknown historical eligibility backfill. Coverage warnings expose missing order projections; a missing existing-order detail returns `ANALYTICS_REBUILD_REQUIRED` rather than invented zeros. Business time is computed from current policy at read time, so policy edits do not require destructive event rewrites.

Range-indexed projection dates, quality dates, approval openings/decisions, cutting facts and overlapping intervals discover candidate orders. Facts are loaded in chunks of 400, not one SQL query per employee/order. Reports do not repeatedly scan full canonical event history per row; individual timeline pages are bounded. Current-month, six-month, source and employee-detail performance are tested with a guarded dedicated synthetic database: **12,000 orders, 336,000 canonical activity events over three years**. Run `tests/analytics-performance.php` only with exact disposable `ARASYA_TEST_DB_NAME=arasya_analytics_performance_test`; it drops/recreates that named fixture DB, never a production database.

Date presets use Romanian-local inclusive calendar days converted to UTC half-open bounds. Custom range is bounded to 366 days; DST spring/fall days are 23/25 hours. Report metadata exposes range, timezone, formula version, grace and snapshot time. Unit/HTTP tests cover exact meters, ownership, rework, overlap, schedules/DST, authorization including accidental grants, policy CSRF/idempotency/conflict, rebuild consistency and concurrent claim/rebuild. MySQL 8.4 and MariaDB 10.11 run the existing full regressions and real Chromium suites. Browser checks include RO/TR, reduced motion and 1440/1024/768/390/360 without horizontal overflow.

Repeated interval calculations reuse report-local calendar/duration results (maximum 8,192 entries per cache), with normal and approval clocks isolated. The instance belongs to a single immutable policy snapshot; nothing survives into a different report or policy edit. Cache saturation falls back to the same calculation, preserving DST, overlapping-window unions and cross-midnight grace. The 15-second / 250-statement CI performance limits remain unchanged. Release validation explicitly requires migration 016, the rebuild CLI, analytics entry points and the read-only B2B identity adapter in addition to checksums.

016 also adds covering canonical activity indexes for `(order_uuid, action, occurred_at)` work proof and the period activity fields actually consumed by employee totals. These two fixed queries explicitly select the new indexes: MariaDB otherwise can choose the legacy order-time index and fetch full event rows. The 12,000-order performance fixture verifies actual `EXPLAIN` index-only reads on both engines (not merely index-condition pushdown) before measuring the unchanged time/query limits. These are additive indexes, not a canonical history rewrite; include their build time and storage in later manual migration planning.

The bounded order timeline starts with `(order_uuid, production_version_after)` and then joins employee names. Its explicit join order prevents MySQL from scanning an employee's unrelated history before applying the order/page filter. Performance tests verify this access plan and the paginated timeline latency; the existing cursor, personnel-only payload and version semantics are unchanged.

Code rollback uses the existing verified release pointer/deployment procedure. Leave additive 016 tables/columns/permission and immutable snapshots intact; never drop production data or roll back migrations as a code rollback. Old 2.14 code remains schema-compatible but does not capture new analytics; before returning to analytics, run the official rebuild for that gap. Approval eligibility during the older-code gap remains unknown, not inferred. Keep verified pre-change DB/config backups per the existing rollout procedure.
