# Production document (PDF) authority (Operations API 2.20.0, Staff 2.9.0, YD SOFT 2.8.0)

Arasya is the single authority for the production ticket of every order whose production it manages. The document engine of 2.16 (immutable revisions, approval-bound revisions, supersession, root revoke, QR binding) is unchanged; this milestone connects the commerce sources (YD SOFT) to it and fences their legacy ticket.

Unchanged: production authority, production QR authority, the 14-stage workflow, ingestion contracts, customer tracking, FAN/AWB, payments and the Meta/PixelYourSite setup.

## What existed and what was missing

| Area | Before 2.20 | 2.20 |
|---|---|---|
| Revisions, approval, supersession, revoke, QR binding | Complete since 2.16 (`DocumentService`, `TicketSnapshot`, migration 017) | Reused unchanged |
| Who prints the workshop ticket of a web order | YD SOFT `PdfEngine` (mPDF), one file per order in `uploads/yd_secure_mes`, overwritten on every regeneration | Arasya revision for Arasya-managed orders; YD ticket only for orders YD SOFT still manages |
| YD access to Arasya documents | None | Signed `orders/documents` (state) and `orders/document` (issue revision 1 + print) |
| Attribution | Employee only | Employee or signed source operator (migration 020) |
| Staff preview / history | Print (download) only | Non-recording preview without QR, revision history |
| Per-source cutover control | None | `ARASYA_SOURCE_DOCUMENT_AUTHORITY_<SOURCE>` and the YD option `yd_arasya_document_authority_mode` |

## Model

- **Document authority of an order** (`DocumentService::documentAuthorityOf`):
  - internal and unmanaged sources (B2B, Trendyol): always `arasya` (unchanged since 2.16);
  - a signed source (Trendhome, OutletPerdele): `arasya` only for its `operations` orders while its document mode is `observe` or `enforce`; otherwise `source`.
- **Revision 1** needs no approval (2.16 rule). It is generated by a Staff document operator, by the B2B handoff, or (document mode `enforce` only) through the signed source contract when the YD operator first opens the ticket. It adopts the order's active QR.
- **Every later revision** needs the 2.16 workflow: a stale or revoked document, a revision request (`production.documents.request_revision`), approval by the revision approver (never the requester), then generation by a document operator. The source can never create, approve or generate it.
- **Current revision**: at most one active revision per order (`uq_production_document_revisions_active`). A stale or revoked document has no printable revision.
- **Commerce updates** never regenerate a document. A change of printed content makes the document stale inside the projection transaction (2.16 `DocumentStaleness`); a commerce-only change (status, payment, price) keeps it.
- **QR**: a revision prints its bound QR, which is the order's single active QR. Downloads, previews, prints and reprints never rotate it. Only a new approved revision (superseded) or a root revoke (revoked) retires it.

## Modes (`ARASYA_SOURCE_DOCUMENT_AUTHORITY_<SOURCE>`)

Default and fallback: `legacy`. `enforce` is accepted only with `ARASYA_SOURCE_QR_AUTHORITY_<SOURCE>=enforce`; any other combination is reported (`document_authority_requires_qr_enforce`) and runs as `observe`. The heartbeat reports `documentAuthorityMode`.

| Mode | YD SOFT ticket | Arasya documents for the source | Signed print |
|---|---|---|---|
| `legacy` | every order | Staff tool as in 2.16 (unused by the source) | refused (`DOCUMENT_AUTHORITY_SOURCE`) |
| `observe` | every order; Arasya-managed generations are logged with the Arasya state | Staff generation for `operations` orders only | refused (`DOCUMENT_CUTOVER_INACTIVE`) |
| `enforce` | only orders YD SOFT manages | Staff, and the source for revision 1 | allowed |

The YD option moves first, like the production and QR fences: YD observe, then Arasya observe; YD enforce, then Arasya enforce; then "Testează conexiunea".

## Interfaces

- `POST /integrations/sources/{source}/orders/documents` `{orderIds: [...]}` (1–50, signed, read-only): per order `exists`, `productionAuthority`, `documentAuthority`, `documentStatus`, `issueAllowed`, `activeRevision {number, generatedAt, prints, qrRevision, qrHint}` (only while the document is usable) and the open `request {status, targetRevision}`. No customer data, no QR payload, no PDF.
- `POST /integrations/sources/{source}/orders/document` `{orderId, issue, revisionNumber|null, actor: {id, name}}` (signed, document mode `enforce`):
  - creates revision 1 when `issue` is true and the open order has no document (never a later revision);
  - refuses `DOCUMENT_REVISION_REQUIRED` (stale), `DOCUMENT_REVOKED`, `DOCUMENT_NOT_GENERATED`, `ORDER_UNAVAILABLE`, `DOCUMENT_REVISION_NOT_ACTIVE`;
  - records the print or reprint attributed to the source operator;
  - answers the order identity, its state, `issued`, `printNumber`, a filename without customer data, the SHA-256 and the PDF (base64) rendered on demand from the immutable snapshot.

  Concurrent requests are serialized by the order row lock: two simultaneous first prints create exactly one revision.
- `GET /production-documents/orders/{id}/revisions/{n}/preview` (Staff/Dashboard document roles): an inline PDF without a scannable QR, marked "PREVIZUALIZARE — NU SE TIPĂREȘTE". Nothing is recorded. Obsolete revisions only for history holders.
- `php bin/document-inventory.php --source=<source>`: read-only bounded inventory (`valid`, `attention`, `pending_approval`, `missing_eligible`, `skipped_closed`, `skipped_source`, `anomaly`). It never creates documents: revision 1 is created when an order's ticket is first printed, never in bulk.
- `php bin/document-revoke.php --order=<source:id> --reason=… [--apply --confirm=<source:id>]`: the root emergency revoke from the server console (same `DocumentService::revoke` as the root-only Dashboard action). It revokes the active revision and every active QR of the order and blocks production; the replacement follows the request and approval path.

## Migration 020 (additive)

`production_document_revisions` and `production_document_prints` gain a nullable source attribution (`*_source_key`, `*_source_actor`) next to the employee column, which becomes nullable. A check constraint requires exactly one attribution on every row. Nothing is created, rewritten or deleted; API 2.19 keeps working on the 020 schema.

## Ticket layout (renderer only; snapshot schema 1 unchanged)

- The product name, colour and variant wrap on up to three lines instead of being cut; a variant that only repeats the colour is printed once.
- When the source sends no whole-line meters, the fourth box shows the explicit piece count of the source (`buc` = "2 buc." → "BUCĂȚI 2 egale"), the same instruction the YD ticket printed ("în două bucăți egale"); the schematic splits accordingly. `1buc.` is read as one piece (the YD ticket printed it as two).
- Options print verbatim (`buc`, `Manopera`). `Elemente`, prices, payment and other Woo meta are not printed.
- Measurement boxes are 36 pt, so four ordinary YD lines fit one A4 page; larger orders paginate with the header, revision and QR on every page.

## YD SOFT 2.8.0

- `DocumentAuthorityFence` (option `yd_arasya_document_authority_mode`) is the single decision point. Under `enforce` (with QR and production fences on `enforce`), for an Arasya-managed or pending order:
  - `PdfEngine::generate` throws before the QR is fetched or the old file is touched;
  - the `yd_generate_pdf` AJAX endpoint refuses direct calls;
  - `yd_download_pdf` refuses to serve the old YD file;
  - the metabox shows "FIȘA DE PRODUCȚIE ARASYA" with "Deschide fișa de producție Arasya".
- `wp_ajax_yd_arasya_document_pdf` (nonce, `edit_shop_orders`) streams the verified Arasya PDF inline. It is never written to disk, order meta or logs. Any refusal shows a Romanian reason and prints nothing; there is no YD fallback.
- `DocumentReconciler` mirrors only `_yd_arasya_document_status`, `_yd_arasya_document_revision` and `_yd_arasya_document_reconciled_at`.
- Admin page "Autoritate fișă de producție (PDF)": the mode (enforce needs a confirmation) and a read-only check of 1–20 orders.
- DB version unchanged (2.7.0).

## Rollback

Before Arasya documents are used, a source returns to `observe` or `legacy` (Arasya key first, then the YD option). Once an Arasya revision was printed or used, keep it: revision history is never deleted, and no historical document is repointed. Orders that already have an Arasya document keep it in every mode (revisions after the first always go through Arasya).
