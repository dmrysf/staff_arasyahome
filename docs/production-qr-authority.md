# Production QR authority (Operations API 2.19.0, Staff 2.8.0, YD SOFT 2.7.0)

Arasya is the only authority for production QR identity. Every canonical order carries Arasya QR references (`order_qr_references`). For operations-managed orders of a source whose QR authority is active, the active reference is the only production QR. The commerce source (YD SOFT) prints it and never invents a competing one.

This milestone covers QR authority only. Production ticket (PDF) authority, customer tracking, FAN/AWB, payments, ingestion and the 14-stage workflow are unchanged.

## QR categories found

| Category | Where | Authority before | After |
|---|---|---|---|
| A. Internal production QR | Arasya intake reference `ARASYA:Q1:…` (issued at ingest, scanned in Staff for resolve, cutting claim and fault acknowledgement) | Arasya (issued) | Arasya; DB-enforced single active; audited rotation |
| B. Production document QR | YD production ticket PDF header (WordPress admin link of the order) | YD SOFT | YD SOFT for source-managed orders; for Arasya-managed orders under QR `enforce` the same PDF prints the active Arasya QR |
| B. Production document QR | Arasya production ticket (document revisions, 017) | Arasya | Unchanged (document revisions bind a QR revision) |
| C. Customer tracking | YD customer portal: email + order/AWB, no QR | YD SOFT | Unchanged |
| D. Logistics | FAN Courier AWB labels/barcodes (generated by FAN) | FAN | Unchanged |

## Model

- **QR revision**: one row of `order_qr_references`. Its number is its position among the order's references, oldest first, and never changes.
- **Active**: at most one per order. Migration 019 adds a stored generated column `active_order_uuid` (set only while `status = 'active'`) with the unique key `uq_order_qr_references_active`, so the database refuses a second active QR. Migration 019 fails and changes nothing if an order already has two.
- **Retired**: `status = 'revoked'` plus `retired_reason`:
  - `superseded`: replaced by a rotation or a new document revision;
  - `revoked`: root document revoke or security;
  - `NULL` for rows retired before 2.19.0, which read as `retired`.
- **Document revisions** (017) bind a QR revision: revision 1 adopts the intake QR, later revisions rotate it. An order with a central document rotates only through its document workflow.
- **Evidence**: `production_qr_events` records `issued`, `rotated`, `revoked`, `reconciled` and `scan_rejected` events. Each event stores the global order ID, revision number, a 10-character SHA-256 hint (never the payload), the mode, the actor, the reason and the time. Rotations are also written to the IAM audit (`production.qr.rotated`), and refused rotations to the security audit (`PRODUCTION_QR_DENIED`).

## Modes (`ARASYA_SOURCE_QR_AUTHORITY_<SOURCE>`)

The QR mode is independent of the ingestion mode and the production authority mode. The default and the fallback for any unreadable value is `legacy`.

| Mode | Source QR answer | Manager rotation | Notes |
|---|---|---|---|
| `legacy` | `qrAuthority: source`, no payload | refused (`QR_CUTOVER_DISABLED`) | today's behaviour |
| `observe` | payload for operations orders | allowed | YD still prints its own code and logs it |
| `enforce` | payload for operations orders | allowed | YD prints only the Arasya QR for its Arasya-managed orders |

`enforce` is accepted only while `ARASYA_SOURCE_AUTHORITY_<SOURCE>=enforce`. Any other combination is reported (`qr_authority_requires_production_enforce`) and runs as `observe`. The heartbeat reports `qrAuthorityMode`; old YD versions ignore it.

## Interfaces

- `POST /integrations/sources/{source}/orders/qr` `{orderIds: [...]}`, 1–50 order IDs, signed:
  - Read-only: it never issues or writes anything.
  - For each order it returns `exists`, `productionAuthority`, `qrAuthority` (`arasya|source`), `qrIssueRequired` and `qr: {payload, revision, hint, issuedAt, documentRevision}`.
  - `qr` is present only when `qrAuthority = arasya`.
  - It never returns customer data.
- `GET /orders/{id}/production-qr` (manager, `production.manage_authority` plus Dashboard access) returns:
  - the authority and mode;
  - the active revision, with its payload and a server-rendered SVG;
  - the history;
  - whether a rotation is allowed.
- `POST /orders/{id}/production-qr/rotate` `{expectedQrRevision, reason: label_lost|label_damaged|security}`, with the `Idempotency-Key` header and CSRF. One transaction:
  1. Lock the order row.
  2. Replay the idempotency key if it was already used.
  3. Check the expected revision.
  4. Retire the active reference as `superseded`.
  5. Issue the next reference.
  6. Write the evidence and the audit.

  A rotation is refused for a source-managed order, a completed order, an unavailable (cancelled) order, an order with a central document, and while the source is `legacy`. Two concurrent rotations leave exactly one active code; the other request gets `409 QR_CHANGED`. The idempotency store never holds a payload.
- `POST /orders/resolve-qr` (Staff scan):
  - **Active code:** the order.
  - **Superseded code:** `410 QR_SUPERSEDED` ("COD QR ÎNLOCUIT…"). The active revision number is shown only to an employee who may see the order.
  - **Revoked code:** `410 QR_REVOKED`. A document-bound code answers `DOCUMENT_SUPERSEDED` or `DOCUMENT_REVOKED`, as before.
  - **Unknown code:** `404 UNKNOWN_QR`, a generic answer that leaks no order.
  - **Malformed input** (for example a YD admin link): `400 INVALID_QR`.
  - Every refused scan of a known code is recorded as `scan_rejected`. Retired codes can never claim cutting work or acknowledge a fault (`DocumentGuard::assertQrUsable`).
- `php bin/qr-reconcile.php --source=<source> [--orders=<id,…>] [--limit=50] [--apply]`, a bounded operator reconciliation of operations orders:
  - A dry run is the default.
  - It keeps every active QR (`reused`) and issues one only where none exists (`issued`).
  - It skips source-managed orders.
  - It reports an anomaly, and repairs nothing, if an order has two active codes (exit code 3).
  - It prints hints, never payloads.

**Never rotates a QR:**
- ingestion (create, update, replay, cancellation);
- commerce updates;
- stage transitions;
- takeovers and releases;
- the source QR answer.

The intake QR is issued exactly once per order. Ingestion re-issues one only for an order left without any active QR, and records that issue.

## Staff 2.8.0

- **Order detail → "Cod QR de producție"** (managers who hold the authority permission and Dashboard access):
  - the authority (Arasya or YD SOFT) and the mode;
  - the active revision, with a white QR preview, the issue time and the hint;
  - the bound document revision;
  - an SVG label download (`ARASYA-QR-<order>-R<n>.svg`, with no customer data in the name);
  - the revision history;
  - "Înlocuiește codul QR", which asks for a reason and an explicit warning confirmation.
- **Scanner:** shows the refusals in strong Romanian words: "COD QR ÎNLOCUIT" (with the active revision) and "COD QR ANULAT".

## Cutover and rollback (per source, Trendhome first)

1. Back up the database and deploy API 2.19.0. Run migration 019 inside the maintenance window. Deploy Staff 2.8.0, then YD SOFT 2.7.0. Every mode stays `legacy`.
2. Set the YD QR mode to "Observare QR", then `ARASYA_SOURCE_QR_AUTHORITY_<SOURCE>=observe`, then run "Testează conexiunea". Pilot one test order:
   - reconcile its QR;
   - scan it in Staff;
   - generate the YD ticket and check that `qr_authority_observed` is logged.
3. Set the YD QR mode to "Blocare QR" (this needs the production fence on `enforce`), then the source to `enforce`, then test the connection. Then accept on a new order:
   - the YD ticket prints the Arasya QR;
   - updates and stage work keep the same code;
   - after a Staff rotation the old code is refused and the new one resolves.
4. Reconcile the existing operations orders with `bin/qr-reconcile.php` (a dry run first, then `--apply`).

**Rollback, before meaningful use:** set the source to `observe` or `legacy` first, then the YD QR mode. No revision history is deleted. A code that is already printed is never reactivated blindly; reissue through a rotation instead.
